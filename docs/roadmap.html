Dispatch · Build Plan

Closing the four competitive gaps

A phased plan to add the features that put Dispatch on the SMB shortlist: quoting, QuickBooks, growth tools, and an open ecosystem — each built on the patterns the app already uses, so nothing is invented from scratch.

Ground rules — how this app already extends

Every item below reuses an established seam. Sticking to them keeps the work small and consistent:

  • CRUD factory — new tables get their REST surface from resource(path, collection, writeCap, {...}) in server.js: org-scoping, pagination, read-gate, audit, and hooks for free.
  • One authz source — add a capability to CAPABILITIES and a page to PAGES in lib/permissions.js; server enforcement and client nav both follow.
  • Feature flags — gate each module behind a FEATURE_FLAGS entry so it's toggleable per workspace from Super Admin (default on, hides when off).
  • Migrations — one dated file in db/migrations/, additive & idempotent (add column/table if not exists), with an RLS policy mirroring 2026-08-11_row_level_security.sql, and every FK indexed.
  • Encrypted secrets — third-party credentials go through lib/crypto.js (encryptSecret/decryptSecret, SECRETS_KEY), exactly as Sage Intacct does today.
  • Verify gate — each phase ships with node --test coverage of the new capability + scoping, per the repo's existing test suite.

P1

Quotes & Estimates

Effort: M · ~4–6 dev-days
Data
Migration 2026-08-24_quotes.sql: quotes (number QUO-####, customer_id, site_id, status draft·sent·approved·declined·converted, valid_until, subtotal/tax/total, signature fields) + quote_lines (mirrors invoice_lines). RLS policy + FK indexes on customer_id/site_id.
API
resource('quotes', …) and resource('quote-lines', …) for CRUD, plus two action routes: POST /api/quotes/:id/convert (→ work order or invoice, snapshotting lines) and POST /api/portal/:token/quotes/:id/approve (customer accept + signature, reusing the WO signature pattern).
Authz
Caps quotes:write (manager, accountant, dispatcher) & quote_lines:write; a quotes page in PAGES; a quotes feature flag.
UI
A Quotes list + QuoteDetail (clone of Invoices.jsx/InvoiceDetail.jsx), a "Convert" button, and a portal quote-approval view (clone of the portal invoice-pay view). Dashboard tile: open quotes + win rate.
Reuse
~70% of invoicing — line editor, number generator, tax math (round2/TERM_DAYS), portal token flow, PDF/export path.
Risk
Low. Main design call: does an approved quote create a work order, an invoice, or let the user pick? Recommend quote → work order (keeps the field-work loop intact), with "bill now" as a shortcut.
Done when
AcceptanceA dispatcher drafts a quote, the customer approves + signs it from the portal, and it converts to a work order whose lines match — with a test asserting cross-tenant and role scoping.
P2

QuickBooks Online integration

Effort: L · ~8–12 dev-days
The wrinkle
Intacct uses static credentials; QuickBooks Online is OAuth2 with a refreshable token. This is the one genuinely new mechanism — the integration layer must store and refresh an OAuth grant, not just encrypted fields.
Data
Reuse the integrations table (already encrypted, per-workspace). Add qbo config holding the encrypted refresh_token, realm_id, and token expiry. Add an external_ref mapping (or a qbo_id column) on customers and invoices so pushes are idempotent (create vs. update).
API
  • GET /api/integrations/quickbooks/connect → Intuit OAuth redirect; GET /api/integrations/quickbooks/callback stores the encrypted refresh token.
  • A token-refresh helper wrapping calls (mirror of resolveIntacctConfig).
  • POST /api/invoices/:id/quickbooks — push/sync (mirror of the existing /api/invoices/:id/intacct), upserting the customer first, then the invoice.
  • Optional inbound: a QBO webhook to mark an invoice paid when reconciled in QuickBooks.
Authz & flags
Add quickbooks to INTEGRATION_FLAGS (Super-Admin per-workspace allowlist), gated by integrationAllowed(); configured under members:write like Intacct.
UI
A QuickBooks card in Settings → Integrations (clone the Intacct card): "Connect to QuickBooks" button → OAuth → connected state + "Sync this invoice" action on InvoiceDetail.
Reuse
The whole integrations spine — encrypted storage, integrationAllowed gating, the settings-card pattern, the push-on-demand route shape. New: OAuth dance + token refresh (use intuit-oauth) and the field/object mapping.
Risk
Medium. OAuth token lifecycle (refresh, revocation), Intuit app review for production, and sandbox vs. prod realms. Scope v1 as one-way push (customers + invoices → QBO); leave payment write-back for v2.
Done when
AcceptanceA manager connects QuickBooks via OAuth, pushes an invoice, and it appears in the QBO sandbox with the customer matched — re-pushing updates rather than duplicating.
P3

Growth tools — reviews, financing, campaigns

Effort: L overall · ship in 3 slices

Three distinct sub-features. Ship smallest-first so value lands early.

3a · Reviews
~2–3 days. On work-order approved, fire a review request via the existing sendEmail/sendSMS senders, using the same afterUpdate hook that already texts "on the way." New review_requests table (sent/clicked), a per-workspace Google review URL in Settings, and a notification-prefs toggle. Highest ROI for the effort.
3b · Financing
~2–3 days, partner-dependent. Add an "Apply for financing" link on portal quotes/invoices pointing to a lender (Wisetack/Sunbelt-style), plus a webhook to record application status. Mostly a link + status field; no underwriting in-app. Best done after quotes (P1) so it attaches to a quote total.
3c · Campaigns
~1–2 weeks. A campaigns table + audience builder (filter customers by region/status/last-service), sent through the email/SMS senders with unsubscribe handling. This is the heaviest slice — treat as its own mini-project; start with "email a saved segment," add scheduling later.
Reuse
Email + SMS infrastructure already exists (senders, per-user prefs, the WO afterUpdate hook, notifications). Reviews and financing are mostly wiring; only campaigns needs net-new UI.
Risk
Compliance: SMS/email consent + unsubscribe (TCPA/CAN-SPAM) must be built into campaigns from day one, not bolted on. Rate-limit sends.
Done when
AcceptanceApproving a work order sends the customer a review link (3a); a portal invoice shows a working financing CTA (3b); a manager emails a filtered customer segment with an unsubscribe footer (3c).
P4

Open ecosystem — booking widget + public API

Effort: L overall · 2 tracks
4a · Booking
~5–7 days. A public, unauthenticated /book/:orgSlug page (new reserved segment) that lists the workspace's service_offers, captures a lead, and creates a work_orders row at status requested — reusing the exact pattern of POST /api/portal/:token/requests, minus the token. Ships as an embeddable <iframe>/script snippet. v1 = request-a-slot; real-time availability from the schedule is a v2 add.
4b · Public API
~5–8 days. A new api_keys table (per-workspace, hashed) and a key-auth middleware that resolves an org + service role, then rides the existing resource() routes — the REST surface is already clean. Add outbound webhooks (a webhooks table + dispatch on events like invoice.paid, work_order.created), reusing the notification dispatch plumbing. That webhook layer is what a Zapier/Make app connects to.
Authz & flags
API keys carry a capability set (default read-only); scope writes explicitly. Booking is public but org-scoped and rate-limited. Both behind feature flags.
Reuse
The portal's no-login pattern for booking; the resource() factory for the API; Stripe-webhook + notification code as the model for outbound webhooks and signature verification.
Risk
Public surfaces need hard rate-limiting and spam/abuse controls (the booking form is unauthenticated — add a simple challenge + per-IP cap). API keys need rotation + scoping. Webhook delivery needs retries + a dead-letter.
Done when
AcceptanceA prospect books from an embedded widget and it lands as a requested work order; an external script authenticates with an API key to read work orders; a test webhook fires on invoice.paid.
